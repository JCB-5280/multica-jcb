# Database Schema

## Overview

MATO uses PostgreSQL 17 with the `pgvector`, `pgcrypto`, and `pg_cron` extensions. The schema has evolved through 92 migration files (numbered roughly 001–092, with some gaps for parallel development). All migrations are in `server/migrations/`.

The database is managed with a custom migration runner (`server/cmd/migrate/`) and sqlc generates type-safe Go query stubs from SQL files in `server/pkg/db/queries/`.

---

## Core Principles

1. **All workspace-scoped tables have `workspace_id UUID NOT NULL REFERENCES workspace(id) ON DELETE CASCADE`.** Deleting a workspace cascades to everything it owns.

2. **All entities use UUID primary keys** generated by `gen_random_uuid()` (from `pgcrypto`).

3. **All tables have `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`** and most have `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`.

4. **Actors are polymorphic.** Anywhere a human or agent can be the author/creator/actor, the column pair is `{role}_type TEXT CHECK (... IN ('member', 'agent'))` and `{role}_id UUID`. These are intentionally not foreign keys (to allow either a `user` or `agent` UUID) — referential integrity is enforced at the application layer.

## pgvector: Currently Installed, Not Used for Skills

The `pgvector` extension is available (it's part of the `pgvector/pgvector:pg17` Docker image used in development and CI). However, **no table in the current schema has a `vector` column**.

The skill system does not use embeddings or semantic search. Skills are retrieved by:
- Exact name match
- Full list scan filtered by workspace_id
- Agent-specific joins

If you want to add semantic skill retrieval (e.g., "find the most relevant skill for this task description"), you would need to:

1. Add a `vector(1536)` column to the `skill` table (size depends on embedding model)
2. Build an embedding pipeline: call an embedding API (OpenAI embeddings, Anthropic, etc.) when skills are created or updated
3. Store the embedding in the vector column
4. Write a cosine similarity query using `<=>` operator
5. Create an `ivfflat` or `hnsw` index for performance

The infrastructure cost is low — pgvector is already installed. The work is the embedding pipeline.

## Performance Notes

### Indexes Worth Knowing

Key indexes that drive performance:

```sql
-- Issue queries (most common query path)
idx_issue_workspace      ON issue(workspace_id)
idx_issue_status         ON issue(workspace_id, status)
idx_issue_assignee       ON issue(assignee_type, assignee_id)

-- Task claim (hot path — runs every few seconds per daemon)
idx_agent_task_queue_claim_candidate  
    ON agent_task_queue(runtime_id, priority DESC, created_at ASC)
    WHERE status IN ('queued', 'dispatched')

-- Timeline queries (keyset pagination)
idx_timeline_keyset  ON activity_log(issue_id, created_at DESC, id DESC)

-- Search (full-text)
idx_issue_search_index  -- tsvector column updated by trigger
```

### Rollup Tables

`task_usage_daily` and `task_usage_dashboard_daily` are pre-aggregated tables populated by `pg_cron`. They make dashboard queries fast but require:

1. Running `pg_cron` (either as a PostgreSQL extension or via cron jobs)
2. Running the backfill utilities to populate historical data
3. Flipping the `UseDailyRollupForRuntimeUsage` / `UseDailyRollupForDashboard` config flags

By default these are disabled — the server reads raw `task_usage` for safety. Only enable rollups after confirming the cron jobs are running and the backfill is complete.
